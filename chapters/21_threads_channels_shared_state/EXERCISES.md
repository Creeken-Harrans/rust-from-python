# 练习：线程、信道与共享状态

## Level 1 练习（3题）

### 练习 1.1：多线程求和

**目标**：理解 `spawn` / `join` 和 `move` 闭包。

**要求**：
1. 创建一个包含 10 个 `u64` 整数的向量 `Vec<u64>`，值为 `[1, 2, 3, ..., 10]`
2. 将该向量分成两半（前5个和后5个）
3. 启动**两个**线程，每个线程负责计算自己那一半元素的**平方和**
   - 第一个线程：计算 `1^2 + 2^2 + 3^2 + 4^2 + 5^2`
   - 第二个线程：计算 `6^2 + 7^2 + 8^2 + 9^2 + 10^2`
4. 使用 `join` 等待两个线程完成，收集各线程的结果
5. 主线程汇总两个部分和，打印最终结果（应该等于 `385`）

**提示**：
- 需要用 `move` 将数据移入线程闭包
- 可以用 `split_at` 或手动构造两个子向量

**验证**：运行程序，确保输出 `385`。

---

### 练习 1.2：简单消息传递

**目标**：理解 `mpsc::channel` 的基本用法。

**要求**：
1. 创建一个 `mpsc::channel<String>()`
2. 启动**3个**生产者线程，每个线程发送 2 条消息，消息内容自定（例如 "Thread 0 - msg 1"）
3. 将原始的 `tx` 克隆给每个线程
4. **在启动所有线程后**，在主线程中 `drop` 原始的 `tx`
5. 主线程通过 `for msg in rx` 循环接收所有消息并打印
6. 统计并打印收到的消息总数（应该等于 6）

**提示**：
- 需要在主线程中 `drop(tx)`，否则信道永远不会关闭
- 可以给消息编号，方便验证

**验证**：程序应该收到恰好 6 条消息。

---

### 练习 1.3：Arc<Mutex<T>> 共享计数器

**目标**：理解 Arc 和 Mutex 的组合使用。

**要求**：
1. 创建一个 `Arc<Mutex<Vec<String>>>`，初始为空 Vec
2. 启动 **5个** 线程，每个线程：
   - 向 Vec 中 `push` 一条消息（例如 "Thread 3 says hello"）
   - 每条消息后 `sleep` 一小段时间（模拟 I/O 操作）
3. 所有线程完成后，主线程打印：
   - Vec 中的总条目数（应为 5）
   - Vec 中的所有消息

**提示**：
- `lock().unwrap()` 返回 `MutexGuard<Vec<String>>`，可以直接调用 `.push()`
- 考虑在打印前对消息排序（因为线程执行顺序不确定）

**验证**：Vec 中应该有 5 条消息。

## Level 2 练习（2题）

### 练习 2.1：并行搜索

**目标**：综合运用线程、move 闭包和结果收集。

**要求**：
1. 生成一个较大的字符串向量（至少 100 个元素），其中包含一些目标字符串
   - 例如：生成 `["item_0", "item_1", "item_2", ...]`，目标为查找包含 `"42"` 的元素
2. 将数据分成 **4** 个大小相近的块（chunk）
3. 为每个块启动一个线程，在线程中：
   - 遍历该块中的每个字符串
   - 如果字符串包含目标子串，记录其索引和内容
4. 每个线程将结果（找到的所有 (索引, 内容) 对）通过**一个共享的 mpsc channel** 发回主线程
5. 主线程收集所有结果，打印找到的条目

**要求**：
- 必须使用 mpsc channel 回传结果（而不是 Arc<Mutex<Vec>>）
- 需要在主线程中 drop 原始 tx

**验证**：程序应该找到恰好一个匹配（例如只包含 "42" 的那一项）。

### 练习 2.2：线程安全的缓存

**目标**：设计一个简单的线程安全数据结构。

**要求**：
1. 实现一个结构体 `ThreadSafeCache`，内部使用 `Arc<Mutex<HashMap<String, String>>>`
2. 提供以下方法：
   - `new() -> Self`：创建空的缓存
   - `insert(key: String, value: String)`：插入键值对
   - `get(&self, key: &str) -> Option<String>`：获取值（克隆返回）
   - `len(&self) -> usize`：返回缓存中的条目数
3. 在 `main` 函数中：
   - 创建一个 `ThreadSafeCache` 实例
   - 启动 10 个线程，每个线程向缓存插入不同的键值对
   - 所有线程完成后，验证缓存中有 10 个条目
   - 尝试用 `get` 读取每个键，验证数据完整性

**提示**：
- `ThreadSafeCache` 需要实现 `Clone`（利用 `Arc::clone`）
- 每个线程需要拿到缓存的克隆
- 考虑使用 `impl Clone for ThreadSafeCache`

**验证**：最终缓存中应该有恰好 10 个条目，且每个条目都能正确读取。

## Level 3 练习（1题）

### 练习 3.1：并行归并排序（Merge Sort）

**目标**：实现一个真正的并行算法，体验多线程带来的性能提升。

**背景**：归并排序是一个经典的分治算法，天然适合并行化：
- 将数组分成两半
- 递归地对两半分别排序
- 合并两个已排序的半数组

**要求**：
1. 实现函数 `parallel_merge_sort<T: Ord + Send + Clone>(arr: &mut [T])`
2. 如果数组长度 ≤ 阈值（例如 1000），使用标准的单线程排序（`arr.sort()` 或手写归并）
3. 如果数组长度 > 阈值：
   - 将数组分成两半（`split_at_mut`）
   - 启动一个**新线程**对左半部分排序
   - 当前线程对右半部分排序
   - 用 `join` 等待子线程
   - 合并两个已排序的半数组
4. 实现函数 `merge<T: Ord>(left: &[T], right: &[T]) -> Vec<T>` 将两个已排序切片合并
5. 在 `main` 中：
   - 生成一个大的随机 `Vec<i32>`（例如 100 万元素）
   - 分别用单线程排序（`sort()`）和并行归并排序计时
   - 打印两种方法的耗时对比

**注意**：
- 对于非常大的数组，需要注意递归深度——不应该对太小的子数组也创建线程
- 可以使用 `rayon` 库作为参考实现，但本题要求**手动实现**

**验证**：
- 并行排序的结果应该与标准库 `sort()` 完全一致
- 在多核机器上，并行版本应该快于单线程版本
- 在单核/双核机器上，线程创建的开销可能抵消并行收益

**扩展思考**：如果你有 16 个核，这个实现的并行度是多少？如何改进以充分利用所有核心？

## 思考题

### 思考题：Rust 的并发安全 vs Python 的 GIL

阅读以下场景并思考：

**场景**：
> 小明用 Python 写了一个 Web 服务器，使用多线程处理请求。因为 Python 有 GIL，
> 他不用担心 Python 对象层面的数据竞争——GIL 保证同一时刻只有一个线程执行 Python 字节码。
> 但他发现他的程序在多核服务器上处理 CPU 密集型请求（如图像处理）时，多线程性能很差，
> 甚至比单线程还慢。
>
> 同样是 Web 服务器，小明用 Rust 重写。Rust 没有 GIL，他的多线程程序在多核上表现很好。
> 但他一开始写 Rust 时遇到了很多困难：编译器不断报错，说 `Rc` 不是 `Send`、`RefCell`
> 不是 `Sync`。他花了半天时间才把 `Rc` 改成 `Arc`、`RefCell` 改成 `Mutex` 让代码通过编译。

**请思考并回答**：

1. **GIL 的利弊**：Python 的 GIL 既保护了数据不被并发破坏，又限制了并行性能。如果在 Rust 中加入类似的 GIL，会有什么后果？Rust 选择了什么样的 trade-off？

2. **编译期 vs 运行时**：小明在 Python 中"不用考虑数据竞争"（因为有 GIL），在 Rust 中"必须考虑，但编译器帮忙检查"。这两种体验有什么本质不同？哪种更能帮助写出正确的并发程序？

3. **Rust 的"困难"是否值得**：小明花了半天改类型（Rc→Arc, RefCell→Mutex）。这半天时间花得值吗？如果在 Python 中遇到数据竞争 bug，修复需要多少时间？

4. **并发模型的哲学**：Rust 说"不要通过共享内存来通信，而是通过通信来共享内存"。这句话的含义是什么？它和 Python 的线程模型有何不同？

5. **如果 Rust 有 GIL**：假设 Rust 也有 GIL，那么 `Send`/`Sync` trait 还有存在的必要吗？为什么？

## 推荐命令

### 新建项目

```bash
# 如果从零开始（不基于本章代码）
cargo new concurrency_exercises
cd concurrency_exercises
```

### 编译与运行

```bash
# 编译（带所有警告）
cargo build

# 运行
cargo run

# Release 模式（优化后的性能）
cargo run --release

# 检查代码风格和潜在问题
cargo clippy

# 如果有测试，运行测试
cargo test

# 查看编译器的详细错误信息
cargo build 2>&1 | less
```

### 调试并发问题

```bash
# 使用 Rust 的线程 sanitizer（需要 nightly 编译器）
RUSTFLAGS="-Z sanitizer=thread" cargo +nightly run

# 打印所有线程的 backtrace（在程序 hang 住时）
# 发送 SIGUSR1 信号给进程
kill -SIGUSR1 <pid>
```

### 性能测量

```bash
# 使用 time 命令简单计时
time cargo run --release

# 使用 hyperfine 进行基准测试（需要安装）
# cargo install hyperfine
hyperfine 'cargo run --release'

# 在代码中使用 std::time::Instant 进行精确计时
```

### 学习资源

```bash
# 在浏览器中打开 Rust 标准库文档
rustup doc --std

# 查看 std::thread 模块
rustup doc --std std::thread

# 查看 std::sync 模块
rustup doc --std std::sync
```
