## 为什么需要学习这一章

在 Rust 中, **所有权 (Ownership)** 是最核心的概念之一, 而所有权的基础就是
对内存 (栈/堆) 的理解。如果你不知道 `String` 的数据在堆上、`.clone()` 会把堆
数据也复制一份, 那你就不可能真正理解为什么 `let s2 = s1` 之后 `s1` 不能再被使用。

具体来说, 不理解栈/堆会导致以下困惑:

- "为什么 i32 可以 Copy, 而 String 不能？"
- "为什么 move 会发生？move 到底在移动什么？"
- "为什么 clone() 比较慢？它在做什么？"
- "什么叫 '数据在栈上' 和 '数据在堆上'？"
- "Drop 被调用了, 但我在代码中并没有看到它 —— 谁调用的？"

这些困惑在本章中都将得到解答。本章是通往所有权的必经之路。

## 背景知识: 栈与堆

### 什么是栈 (Stack)

栈是操作系统为每个线程分配的一块连续内存区域, 以 **LIFO (Last In, First Out,
后进先出)** 的方式工作。

**类比: 叠盘子**

想象一摞盘子:

```
    ┌───┐
    │ D │  ← 刚放上去 (push)
    ├───┤
    │ C │
    ├───┤
    │ B │
    ├───┤
    │ A │  ← 最早放上去的
    └───┘
```

你只能在顶部放盘子 (push), 也只能从顶部取盘子 (pop)。
你**不能**从中间抽走一个盘子 —— 上面的必须先取走。

栈的操作正是如此:

```
PUSH 42:                PUSH 99:                POP → 99:
┌──────┐                ┌──────┐                ┌──────┐
│ 42   │ ← sp           │ 99   │ ← sp           │ 42   │ ← sp
├──────┤                ├──────┤                ├──────┤
│      │                │ 42   │                │      │
├──────┤                ├──────┤                ├──────┤
│      │                │      │                │      │
└──────┘                └──────┘                └──────┘
(sp = stack pointer)    (sp = stack pointer)    (sp = stack pointer)
```

**栈的特点:**

- **快速**: 分配/释放只需移动栈指针 (sp), 通常只需要一条 CPU 指令
- **固定大小**: 每个栈帧 (stack frame) 的大小必须在编译期确定, 以便编译器计算偏移量
- **自动管理**: 函数调用时 push 新的栈帧, 返回时 pop — 全是自动的
- **有限空间**: 栈空间通常较小 (Linux 默认约 8 MB), 超出会导致 stack overflow (栈溢出)
- **LIFO 顺序**: 释放顺序严格等于创建顺序的逆序

**什么数据放在栈上:**
- 固定大小的基本类型: `i32`, `f64`, `bool`, `char`
- 固定大小的数组: `[i32; 5]`
- 所有字段都是固定大小的结构体或元组
- 引用 (本质上是指针, 固定 8 bytes on 64-bit)
- 不可变引用 `&T` 和 可变引用 `&mut T`

**关键概念: 函数调用时的栈帧**

```
调用 main():
┌────────────────────┐
│ main 的栈帧         │ ← sp
│   - 局部变量        │
│   - 返回地址        │
├────────────────────┤
│ 之前的栈帧...       │
└────────────────────┘

调用 foo():
┌────────────────────┐
│ foo 的栈帧          │ ← sp (栈向下增长)
│   - 局部变量        │
│   - 参数            │
│   - 返回地址        │
├────────────────────┤
│ main 的栈帧         │
├────────────────────┤
│ 之前的栈帧...       │
└────────────────────┘

foo() 返回:
┌────────────────────┐
│ main 的栈帧         │ ← sp (回到之前的位置)
├────────────────────┤
│ 之前的栈帧...       │
└────────────────────┘
```

### 什么是堆 (Heap)

堆是进程中的一块较大的内存区域, 用于存放**编译期大小未知或动态变化**的数据。

**类比: 餐厅入座**

想象一家没有预约的餐厅:

```
                    ┌──┬──┬──┬──────────────┬──┬──┬──┐
                    │🪑│🪑│🪑│ (空闲)       │🪑│🪑│🪑│
                    └──┴──┴──┴──────────────┴──┴──┴──┘
                                    ↑
                             "有 4 人的空位吗？"
                                    │
                              ┌─────┘
                              │ 服务员查找空闲区域
                              │ 找到后带你入座
                              │ 吃完后, 服务员标记该区域空闲
                              ▼
                    ┌──┬──┬──┬──┬──┬──┬──┬──┬──┐
                    │🪑│🪑│🪑│你│你│你│你│🪑│🪑│
                    └──┴──┴──┴──┴──┴──┴──┴──┴──┘
                           ↑
                      找到 4 人空位, 分配给你
```

- 你要一个 4 人的桌子 (分配内存), 服务员 (内存分配器) 在空闲区域找
- 这个桌子可能在餐厅的任何位置 (内存地址不确定)
- 吃完后, 桌子归还, 服务员可以给下一个客人 (释放内存)
- 如果你需要更大的桌子 (扩容), 可能需要换桌 (reallocate)

**堆的特点:**

- **灵活**: 可以分配任意大小的内存块, 可以在运行时动态增长
- **较慢**: 分配需要搜索空闲块, 释放需要归还给分配器
- **大容量**: 堆空间远大于栈 (通常仅受物理内存 + swap 限制)
- **不保证释放顺序**: 两个堆分配可以以任意顺序释放
- **需要指针间接访问**: 你在栈上存一个指针, 指针指向堆上的实际数据

**什么数据放在堆上:**
- `String` 的实际字节内容
- `Vec<T>` 的实际元素
- `Box<T>` 的内容 (显式堆分配)
- `HashMap`, `HashSet` 等集合的内部数据
- 任何运行时大小动态的类型 (`dyn Trait`)

---

### 为什么需要两种内存区域

如果只有栈:
- 你不能返回一个动态大小的数据 (因为调用者的栈帧大小在编译期固定)
- 你不能在运行时决定数组的大小
- 你不能创建互相引用的大型数据结构

如果只有堆:
- 每个 `i32` 都要 malloc, 性能会急剧下降
- 大量小对象导致严重的内存碎片
- 每次函数调用都要堆分配, 慢到不可接受

**分工**: 栈负责 "快而小" 的数据 (固定大小, 作用域内), 堆负责 "大而灵活" 的数据
(动态大小, 可能跨作用域传递)。

## 什么是指针 (Pointer)

**本章可能是你第一次接触指针**, 所以让我们从零开始解释。

### 指针就是门牌号

想象内存是一栋巨大的公寓楼, 每个字节是一个房间, 每个房间有唯一的门牌号 (地址)。

```
地址:  0x1000  0x1001  0x1002  0x1003  0x1004  0x1005  0x1006  0x1007
      ┌──────┬──────┬──────┬──────┬──────┬──────┬──────┬──────┐
内容:  │  72  │ 101  │ 108  │ 108  │ 111  │  0   │  ... │  ... │
      └──────┴──────┴──────┴──────┴──────┴──────┴──────┴──────┘
        ^
        │
   指针 P = 0x1000  (存储的是"第一个字节的地址")
```

当你写 `let ptr: &u8 = &some_value;`, `ptr` 变量存储的不是数据本身, 而是数据
在内存中的 **地址**。访问数据时, 需要经过 "解引用 (dereference)" — 即 "去那个
地址看看里面有什么"。

### 为什么需要指针？

1. **共享数据**: 多个地方需要访问同一块数据时, 不需要复制整个数据, 只需要传递
   指针 (8 bytes)
2. **间接访问**: 堆上的数据不能直接放在栈上 (因为大小动态), 必须在栈上放指针
3. **大型数据传递**: 传递一个 1 MB 的数组时, 传指针 (8 bytes) 比复制整个数组
   (1 MB) 快得多

### 类比: 图书馆检索号

- 书的内容 = 数据本身 (在堆上)
- 检索号 = 指针 (在栈上)
- 你要找书, 先看检索号, 再根据检索号去书架上找

### 在 Rust 中:

- `i32` 直接存储值, 没有指针 (数据在栈上)
- `String` 在栈上存储 `{ptr, len, cap}`, `ptr` 指向堆上的 UTF-8 字节
- `&String` 在栈上存储一个指针, 指向栈上的 `String` 结构体
- `Box<i32>` 在栈上存储一个指针, 指向堆上的 i32
- `&[i32]` (slice 引用) 在栈上存储 `{ptr, len}`, 指向某处的连续 i32 数据

## RAII: 资源获取即初始化

RAII (Resource Acquisition Is Initialization, 资源获取即初始化) 是 Rust 内存管理
的核心理念。这个名字来自 C++, 但 Rust 将它发挥到了极致。

### 核心思想

**资源的生命周期 = 持有它的变量的作用域。**

换句话说:
- 变量**创建**时, 它持有的资源 (内存/文件句柄/锁等) 被分配
- 变量**离开作用域**时, 其 Drop trait 的 `drop()` 方法被自动调用, 资源被释放
- 你**永远不需要**手动调用 `free()` 或 `close()`

### 图解

```
{
    let r = Resource::new("my_res");  // ← (1) 资源获取 (Constructor 运行)
    // r 在此作用域内有效
    // ...
} // ← (2) 资源释放 (Drop::drop() 自动调用)
  //     Rust 编译器自动在此插入 drop(&mut r) 的调用
```

### Drop 顺序: LIFO

如果在一个作用域内创建了多个实现了 Drop 的值, **析构顺序是创建顺序的逆序** —
就像一个栈:

```rust
{
    let a = Resource::new("A");  // 创建 A
    let b = Resource::new("B");  // 创建 B
    let c = Resource::new("C");  // 创建 C
    // 离开作用域时:
    //   drop(c) → "释放 Resource: C"
    //   drop(b) → "释放 Resource: B"
    //   drop(a) → "释放 Resource: A"
}
```

这个顺序保证了一个资源不会在使用它的另一个资源释放之前被释放。

### 手动提前释放

如果你需要在作用域结束前释放一个值, 使用 `drop()`:

```rust
let x = Resource::new("early");
drop(x);  // 主动释放, 不等作用域结束
// x 此后不可用
```

注意: `drop()` 不是 C 的 `free()` — 它只是调用 Drop trait, 并**使值变为不可用**
(编译器会在编译期阻止后续使用)。

## 为什么 Rust 不需要 GC 也不需要手动 free

这是 Rust 最令人惊叹的特性之一: 它在编译期就精确地知道在什么位置插入释放代码,
既不需要运行时的垃圾回收器 (GC), 也不要求程序员手动管理内存 (手动 free)。

### 三种内存管理策略对比

| 策略 | 代表语言 | 优点 | 缺点 |
|------|---------|------|------|
| 手动管理 | C, C++ | 零开销, 完全控制 | 容易出错 (double free, use-after-free, 内存泄漏) |
| 垃圾回收 (GC) | Python, Java, Go, C# | 安全, 不需要关心释放 | 运行时开销, 暂停 (stop-the-world), 不可预测的释放时机 |
| RAII + 所有权 | Rust | 零开销, 编译期保证安全, 无需 GC | 学习曲线陡峭 (编译器严格) |

### Rust 的做法

Rust 编译器在编译期执行以下分析:

1. **所有权分析**: 追踪每个值在哪个作用域中"活着"
2. **Drop 插入**: 在值离开作用域的位置自动插入 `drop()` 调用
3. **借用检查**: 确保没有悬垂引用 (dangling reference)

由于所有决策在**编译期**完成, 运行时没有任何开销 — 没有引用计数, 没有 GC 扫描,
没有 stop-the-world 暂停。

### 类比

- **手动 free**: 你出门前需要逐一检查所有电器是否关闭 — 容易漏掉
- **GC**: 有一个管家每小时巡视一圈, 关掉不用的电器 — 省心但有开销
- **Rust RAII**: 电器在出厂时就内置了 "离开房间自动关闭" 的功能 — 零开销零遗漏

## String 内部结构详解

`String` 是理解 Rust 栈/堆关系的最佳例子。

### 内存布局

```
栈 (Stack)                        堆 (Heap)
┌──────────────────────┐          ┌──────────────────────────┐
│ ptr   → ─────────────┼──────→   │ H │ e │ l │ l │ o │ ... │
│ len   = 5            │          └──────────────────────────┘
│ cap   = 8            │          ↑
└──────────────────────┘          实际 UTF-8 字节存在这里
  ↑
sizeof(String) = 24 bytes
(在 64 位系统上, ptr=8, len=8, cap=8)
```

### 三个字段的含义

- **ptr** (pointer): 指向堆上分配的字节数组的第一个字节。类型是 `*mut u8` (指向字节的原始指针)
- **len** (length): 当前有效的字节数。对 `String::from("Hello")` 来说 len=5
- **cap** (capacity): 堆上已分配的总字节数。`cap >= len`, 多余的空间用于未来增长

### 为什么预留容量 (capacity)?

每次 `push` 不需要重新分配内存:

```rust
let mut s = String::with_capacity(10); // 堆上分配 10 bytes
s.push_str("Hi");  // 直接写入, 不需要重新分配 (len 从 0 变为 2)
s.push_str("Rust"); // 直接写入, 不需要重新分配 (len 从 2 变为 6)
```

如果没有预留容量, 每次 push 都可能触发重新分配 (reallocation) — 在堆上找一块新的、
更大的空间, 复制所有旧数据, 释放旧空间。这很慢。预留容量可以避免频繁的重新分配。

### 关键洞察

`size_of::<String>()` 返回的是 24 (在 64 位系统上), 这只是栈上句柄的大小。
**实际字符串数据的大小不计入 `size_of`**。这解释了为什么 `String` 看起来
"很小", 但实际上可以存储 GB 级别的文本 — 因为数据在堆上。

## 栈 vs 堆: 什么放在哪里, 为什么重要

### 决策表

| 情况 | 放在哪里 | 原因 |
|------|---------|------|
| 编译期已知大小的基本类型 | 栈 | 快速分配, 无需间接访问 |
| 函数中的固定大小数组 | 栈 | 大小在编译期确定 |
| 结构体 (字段都是固定大小) | 栈 | 整个结构体大小在编译期确定 |
| String 的实际字节内容 | 堆 | 运行时才知道大小, 且可能增长 |
| Vec 的元素 | 堆 | 元素数量运行时可变 |
| Box\<T\> 的内容 | 堆 | 显式要求放在堆上 (可能因为数据太大) |
| 递归数据结构 (如链表节点) | 堆 | 编译期无法确定完整大小 |
| dyn Trait 对象 | 堆 (通常) | 大小在编译期未知 |

### 性能影响

- **栈分配**: 约 1 条 CPU 指令 (移动栈指针)
- **堆分配**: 需要内存分配器搜索空闲块, 可能涉及系统调用 — 慢几个数量级
- **栈访问**: CPU 缓存友好 (空间局部性好)
- **堆访问**: 可能分散在内存各处, 缓存命中率较低

### 对所有权的影响 (预告)

因为栈上数据 (Copy 类型) 复制时只需复制固定大小的几个字节 (通常 1-16 bytes),
所以 Rust 让它们默认为 Copy。而堆上数据 (如 String) 如果逐位复制, 会导致两个
"句柄" 指向同一块堆内存, 当它们同时析构时会产生 double free。

这就是为什么 `i32` 是 Copy, 而 `String` 不是 — 不是风格偏好, 而是**内存安全
必然要求**。

## 代码走读

### 1. Resource 结构体

```rust
struct Resource {
    name: String,
}

impl Drop for Resource {
    fn drop(&mut self) {
        println!("  <- 释放 Resource: \"{}\"", self.name);
    }
}
```

`Resource` 有一个 `String` 字段, 这意味着:
- `Resource` 的栈上部分包含一个 String 句柄 (24 bytes) + name 字段的偏移
- 当 `Resource` 被 drop 时, 首先打印日志, 然后 Rust 自动调用 `self.name` 的
  drop (即 `String` 的 drop), 这会释放堆上的字节
- 这一切都是自动的、递归的 — 你不需要写任何释放代码

### 2. demonstrate_stack()

该函数逐一展示了:
- 基本标量类型及其 `size_of`
- 固定大小数组的栈上存储
- 元组的大小和对齐
- `StackData` 结构体的大小
- 引用 `&T` 的大小 (8 bytes on 64-bit)

关键学习点: 所有这些类型的大小在编译期就确定了, 因此可以完全放在栈上。

### 3. demonstrate_heap()

该函数展示了:
- `String` 的 `size_of` 仅为 24 bytes (句柄), 实际数据在堆上
- `Vec<i32>` 同样 24 bytes
- `Box<T>` 仅为 8 bytes (一个指针)
- 无论 `Box` 指向多大的数据, `size_of::<Box<T>>()` 始终等于指针大小

关键学习点: 堆分配的类型在栈上只放 "控制块" (指针+元数据), 实际数据在堆上。
`size_of` 反映的是栈上部分的大小。

### 4. demonstrate_scope_and_drop()

该函数通过三个例子展示 RAII:
- **同一作用域**: Drop 顺序 = 创建顺序的逆序 (LIFO)
- **嵌套作用域**: 内层作用域结束只释放内层的变量
- **手动 drop**: `drop()` 可以提前释放

关键学习点: Drop 是自动的、确定的、LIFO 顺序的。

### 5. string_internals_demo()

该函数深入:
- 创建 String 并打印 `len` 和 `capacity`
- 演示 `push_str` 如何触发 `capacity` 增长
- 用 ASCII 图示展示内存布局

关键学习点: capacity 的存在避免了每次 push 都重新分配。

## 与 Python 的对照

### Python 模型

```python
x = 42
y = "hello"
z = [1, 2, 3]
```

在 Python 中:
1. **一切皆对象**: `42` 是 `int` 对象, `"hello"` 是 `str` 对象, `[1,2,3]` 是 `list` 对象
2. **所有对象都在堆上**: Python 的栈只存放 "指向对象的指针"
3. **变量名只是标签**: `x`, `y`, `z` 是绑定到对象的名称, 不是存储位置
4. **引用计数**: 每个对象维护一个引用计数, 当计数归零时, 对象被释放
5. **循环 GC**: 除了引用计数, 还有定期扫描循环引用的 GC

```
Python 内存模型:
┌──────────────────────────────────────────────┐
│  栈 (CPython 内部)                            │
│  ┌────────┬────────┬────────┐                │
│  │ x→*    │ y→*    │ z→*    │  (指针)        │
│  └───┼────┴───┼────┴───┼────┘                │
│      │        │        │                      │
│      ▼        ▼        ▼                      │
│  ┌──────┐ ┌──────┐ ┌──────────┐  堆          │
│  │ int  │ │ str  │ │ list     │              │
│  │ ref:1│ │ ref:1│ │ ref:1    │              │
│  │ val:42│ │"hello"│ │[1,2,3]  │              │
│  └──────┘ └──────┘ └──────────┘              │
└──────────────────────────────────────────────┘
```

### Rust 模型

```rust
let x = 42;
let y = String::from("hello");
```

在 Rust 中:
1. **不是一切皆对象**: 基本类型 (i32, f64, bool) 是值, 不是对象
2. **数据可以只在栈上**: `x = 42` 直接在栈上, 没有指针, 没有引用计数
3. **变量名是存储位置**: `x` 是栈上的 4 字节插槽, 直接存放 42
4. **无运行时开销**: i32 的赋值不需要分配、不需要引用计数增减
5. **编译期保证安全**: Rust 在编译期验证所有生命周期, 不需要运行时检查

```
Rust 内存模型:
┌──────────────────────────────────────────────┐
│  栈                                           │
│  ┌──────────┬──────────────────────┐         │
│  │ x = 42   │ y: {ptr, len, cap}   │         │
│  │ (4 bytes)│      (24 bytes)      │         │
│  └──────────┴──────┬───────────────┘         │
│                    │ ptr 指向 ↓               │
│                    ▼                          │
│               ┌──────────┐   堆               │
│               │ H e l l o │                   │
│               └──────────┘                    │
└──────────────────────────────────────────────┘
```

### 核心区别总结

| 方面 | Python | Rust |
|------|--------|------|
| 基本类型存储 | 堆上的对象 | 栈上的值 |
| 内存管理 | 引用计数 + 循环 GC | 编译期 RAII + 所有权 |
| 运行时开销 | 每次赋值都增减引用计数 | 无运行时开销 (i32) |
| 释放时机 | 不确定 (GC 决定) | 确定 (离开作用域即释放) |
| 你需要关心内存吗 | 几乎不需要 | 需要理解, 但编译器帮助你 |
| "5 + 3" 的开销 | 创建新 int 对象, 分配堆内存 | 直接在寄存器中计算 |
| 数组扩容 | 自动 (list.append) | 自动, 但你可以看到 cap 变化 |

### 为什么 Python 隐藏了这些, 而 Rust 显式化?

Python 的设计哲学是 "让简单的事情保持简单" — 你不需要关心内存, GC 替你打理一切。
但代价是:
- 每个整数都是一个堆分配的对象 (在 CPython 中, 小整数有缓存, 但仍然是指针)
- `a = a + 1` 实际上创建了一个新对象
- 内存使用不够透明

Rust 的设计哲学是 "零开销抽象" — 你不为不使用的功能付费。显式的内存模型让你能够:
- 写出高性能代码 (无 GC 暂停, 无引用计数开销)
- 精确控制内存布局
- 在编译期消除内存错误

你之所以 "不用考虑" Python 的内存, 是因为 Python 替你承担了运行时开销。
你之所以 "需要考虑" Rust 的内存, 是因为 Rust 把控制权交给了你 — 并且让
编译器在编译期就帮你检查是否安全。

## 常见错误与误解

### 1. "size_of::\<String\>() 返回的是整个字符串的大小"

**错误**。`size_of::<String>()` 只返回栈上句柄的大小 (通常 24 bytes)。
字符串的实际内容在堆上, 不计入 `size_of`。

### 2. "所有数据都在堆上"

**错误**。基本类型 (i32, f64, bool 等) 和固定大小数组在栈上。只有动态大小
的数据才放在堆上。

### 3. "Box\<i32\> 的 size_of 是 size_of::\<i32\>() + 指针大小"

**错误**。`size_of::<Box<i32>>()` 仅返回指针大小 (8 bytes on 64-bit)。
`Box` 将数据放到堆上, 栈上只留指针。

### 4. "Copy 类型和 Clone 类型没有区别"

**错误**。Copy 类型通过逐位复制实现, 原变量在复制后仍然可用。Clone 类型
的 `clone()` 可能涉及堆分配 (如 `String::clone()`)。`let s2 = s1` 对 Copy
类型是复制, 对非 Copy 类型是 move。

### 5. "Drop 是手动调用的"

**错误**。Drop 在绝大数情况下是自动的。`drop()` 函数是用于**提前**释放的
特殊情况。正常代码中你几乎从不需要手动调用 `drop()`。

### 6. "Rust 的 String 和 Python 的 str 一样"

**不同**。Python 的 `str` 是不可变的, 每次修改都创建新对象。Rust 的 `String`
是可变的, 可以在原始堆缓冲区上就地修改 (如果 capacity 允许)。

### 7. "capacity 大于 len 时, 多余的空间浪费了"

部分正确, 但这是一种有意的权衡: 用少量空闲空间换取避免频繁的重新分配。
类似于餐厅比当前客人数量多准备几个座位。

### 8. "我可以从栈上返回一个局部变量的引用"

**错误**。这是 Rust 编译器会阻止的典型错误:

```rust
fn dangle() -> &String {
    let s = String::from("hello");
    &s  // 编译错误! s 在函数结束时被 drop, 引用变成悬垂
}
```

### 9. "drop 顺序不重要"

**重要**。drop 的 LIFO 顺序保证了资源依赖不被打破。例如, 如果一个结构体 A
包含对结构体 B 的引用, 那么 B 必须在 A 之后析构。

## 重要提醒: "栈 vs 堆"模型并非全貌

本章介绍的栈/堆模型是一种**有用的近似**和心智模型。在实际中, 情况可能更复杂:

### 1. 编译器的优化可能改变实际内存位置

Rust 编译器 (LLVM) 可能将本应放在栈上的值优化到寄存器中, 或者将堆分配内联到
栈上 (如果编译器能证明数据生命周期足够短且大小足够小)。

### 2. 全局/静态变量在单独的内存区域

`static` 和 `const` 变量存储在数据段 (data segment / BSS), 既不在栈也不在堆上。

### 3. 原地 (In-place) 构造

某些情况下, 数据直接构造在最终位置, 没有 "栈 → 堆" 的移动。例如返回值优化 (RVO,
Return Value Optimization) 可使返回的 String 直接在调用者的栈帧中构造。

### 4. OS 层面: 虚拟内存

从操作系统的角度看, 栈和堆都是进程虚拟地址空间中的区域, 由 OS 按需映射到物理内存。
OS 层面的内存管理远比 "栈是快速的、堆是慢速的" 复杂。

### 5. Arena / 自定义分配器

Rust 支持自定义分配器, 可以将数据分配到栈上、到 arena 中、到共享内存中等。
"堆" 只是默认的全局分配器 (Global Allocator)。

### 学习建议

将本章的模型作为 **初始心智模型**, 在掌握之后, 再逐步了解编译器优化和高级内存
管理技术。核心直觉是正确的: 固定大小 = 栈友好, 动态大小 = 需要堆。

## 本章小结

1. **栈 (Stack)**: LIFO 结构, 存放固定大小的数据, 分配/释放极快, 但空间有限
2. **堆 (Heap)**: 动态内存区域, 存放运行时大小可变的数据, 灵活但较慢
3. **RAII**: 资源在变量初始化时获取, 在变量离开作用域时自动释放 (Drop)
4. **Drop 顺序**: LIFO — 后创建的先析构
5. **String 内部**: 栈上 24 bytes = `{ptr, len, cap}`, 实际字节在堆上
6. **Box\<T\>**: 将任意类型放到堆上, 栈上只留一个指针 (8 bytes)
7. **Copy vs 非 Copy**: Copy 类型直接按位复制 (栈上), 非 Copy 类型涉及移动或堆分配
8. **Rust vs Python**: Rust 显式区分栈/堆并给你控制权, Python 隐藏这些细节但付出 GC 开销
9. **零开销**: Rust 的内存管理决策在编译期完成, 运行时无 GC 暂停、无引用计数开销
10. **下一章**: 本章建立了栈/堆的直觉, 为理解所有权 (Ownership)、借用 (Borrowing)、
    生命周期 (Lifetime) 铺平道路

## 下一章衔接

理解了栈和堆之后, 你就有了理解 **所有权 (Ownership)** 的基础。

所有权规则的精髓:

```
┌─────────────────────────────────────────────────┐
│         Rust 所有权三规则                         │
│                                                   │
│  1. 每一个值都有一个所有者 (Owner)                │
│  2. 同一时刻只能有一个所有者                      │
│  3. 当所有者离开作用域, 值被 Drop                 │
│                                                   │
│  这三条规则, 加上 Copy/Move 的区别,               │
│  让你在编译期就消灭了:                            │
│    - double free (重复释放)                       │
│    - use-after-free (释放后使用)                  │
│    - dangling pointer (悬垂指针)                  │
│    - data race (数据竞争)                         │
└─────────────────────────────────────────────────┘
```

现在你已经知道:
- 栈上的数据 Copy 着走, 轻松安全 (i32, f64, bool...)
- 堆上的数据 Move 着走, 所有权唯一 (String, Vec, Box...)
- Drop 在作用域结束时自动运行

下一章, 我们将正式学习所有权、Move 语义、Clone 与 Copy trait, 并用 `cargo run`
亲眼见证编译器的借用检查器如何工作。
