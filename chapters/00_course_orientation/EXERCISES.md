### 练习 1-1：观察编译器错误

**目标**：亲身体验 Rust 编译器的错误信息质量。

**步骤**：

1. 打开 `src/main.rs`，找到 `demonstrate_immutability` 函数中的 `let message` 声明。
2. 在第 69 行后面添加一行：`message = "尝试修改";`（注意不要给 `message` 加 `mut`）。
3. 运行 `cargo build`，观察编译失败。
4. **仔细阅读**编译器给出的错误信息，特别关注：
   - 错误出现在第几行？
   - 编译器建议了哪些修复方案？
   - 错误信息中是否包含了代码上下文？
5. 将添加的那一行**删除**，恢复代码到可编译状态。
6. 运行 `cargo build` 确认程序再次编译通过。

**检查方式**：

```bash
# 确认当前代码可以通过编译
cargo build

# 确认程序运行正常
cargo run
```

**思考**：对比你见过的 Python `TypeError` 或 `AttributeError` 的错误堆栈，Rust 编译器的错误信息给你什么感觉？它是「骂你」还是「教你」？

### 练习 1-2：修改横幅内容

**目标**：理解如何修改 Rust 源代码并重新编译运行。

**步骤**：

1. 打开 `src/main.rs`，找到 `print_banner()` 函数。
2. 修改横幅中的章节描述文字，例如将 `"第 00 章：课程导览 —— 认识 Rust 与系统编程"` 改为 `"第 00 章：课程导览 —— [你的名字] 的学习笔记"`。
3. 修改 `println!` 中的 `COURSE_NAME`，在课程名称后面追加 `"（个人学习版）"`。注意：你需要修改的是 `const COURSE_NAME` 的值，而不是在 `print_banner()` 中拼接字符串（提示：直接修改常量定义）。
4. 还可以尝试修改装饰框的字符（比如把 `╔` 改成 `+`），体会 ASCII 艺术的美感。
5. 运行 `cargo run`，确认新的横幅正确显示。
6. 保存修改（可选：使用 `git diff` 查看你改了什么）。

**检查方式**：

```bash
cargo run | head -8
```

你应该看到修改后的横幅，包含你的自定义文字。

**扩展**：如果你熟悉 Python，心里默默对比一下：要把一个 Python 脚本中的常量值改掉，需要几步？在 Rust 中需要几步？步骤数一样吗？

### 练习 1-3：修改对照表内容

**目标**：通过修改现有数据，熟悉 Rust 字符串的格式控制。

**步骤**：

1. 打开 `src/main.rs`，找到 `compare_with_python()` 函数。
2. 在对照表中新增一行，维度叫 **「泛型支持」** ，Rust 列写 `「编译期单态化（Monomorphization）」`，Python 列写 `「运行时多态（duck typing）」`。
3. 你需要修改表格的 ASCII 框线，确保新行与原有格式对齐。提示：
   - 表格使用 Unicode 制表符：`│`, `├`, `┼`, `┤`, `└`, `┴`, `┘`
   - 每一行的列宽分别约为 22 和 28 个字符（因为中文字符占 2 个英文字符宽度）
   - 你可能需要调整 `println!` 中的空格数来让文字对齐
4. 运行 `cargo run`，确认对照表显示正常，新行与其他行对齐。
5. 观察输出的表格，如果文字没有对齐，调整空格数量直到满意。

**检查方式**：

```bash
cargo run | grep -A2 "泛型支持"
```

**提示**：由于中文字符在终端中宽度不完全一致（取决于终端和字体），对齐不必追求像素级完美。重点在于理解 Rust 中如何通过 `println!` 控制格式化输出。

### 练习 2-1：用 const 和函数组合打印一个「知识点卡片」

**目标**：练习定义常量、编写带返回值的函数、格式化输出。

**要求**：

```rust
print_knowledge_card();
```

### 练习 2-2：编写一个「编译型 vs 解释型」对比函数

**目标**：将本章的表格知识转化为代码，练习函数调用和格式化打印。

**要求**：

1. 新建一个函数 `fn compare_execution_models()`，不接受参数，不返回值。
2. 在该函数中，使用 `println!` 打印一个包含以下三列的对比表：
   - **特征**（6 行：执行方式、首次运行速度、后续运行速度、内存占用、启动时间、典型性能）
   - **编译型**（对应每行的说明）
   - **解释型**（对应每行的说明）
3. 表格格式可以使用简单的 `|` 分隔和对齐，不需要复杂的 Unicode 框线。
4. 在 `main()` 函数中（`compare_with_python()` 调用之后）调用这个新函数。
5. 为新函数添加 `///` 文档注释。

**示例输出格式**：

```
【编译型 vs 解释型】

  特征            | 编译型                    | 解释型
  ----------------+---------------------------+---------------------------
  执行方式        | 源码→编译器→机器码→CPU   | 源码→解释器逐行翻译执行
  首次运行速度    | 需要编译，但编译后极快    | 立即运行，但执行较慢
  后续运行速度    | 极快（无需重新编译）      | 同样慢（每次都要解释）
  内存占用        | 极低（无解释器）          | 较高（解释器驻留内存）
  启动时间        | 极短                      | 需要初始化解释器
```

**检查方式**：

```bash

cargo run     # 对比表应出现在 Rust vs Python 对照表之后
```

**提示**：
- 表格的列宽可以预设固定值，比如特征 18 字符、编译型 28 字符、解释型 28 字符

### 练习 3-1：将 Rust 的特性列表抽取为独立的常量数组

**目标**：理解 `const` 与函数作用域的关系，练习数据结构抽取。

**当前状态**：`show_key_features()` 函数内部定义了一个局部变量 `features`（元组数组），直接在函数内硬编码和打印。

**要求**：

1. 在文件顶部（`main()` 函数之前）新增一个 `const FEATURES: [(&str, &str); 5]`，将五大特性的名称和描述从 `show_key_features()` 中「提升」到模块级别作为编译期常量。
2. 修改 `show_key_features()` 函数，删除内部的局部 `features` 变量，改为引用顶层的 `FEATURES` 常量。
3. 增加一个新函数 `fn find_feature(keyword: &str) -> Option<&str>`，接受一个关键字（如 `"Memory Safety"`、`"No Garbage Collector"` 等），遍历 `FEATURES` 数组，如果找到匹配的特性名就返回其描述，否则返回 `None`。
4. 在 `main()` 函数中调用 `find_feature("Static Typing")` 和 `find_feature("没有这个特性")`，打印返回结果：
   - 对于找到的特性，打印 `"找到特性：{name} —— {description}"`
   - 对于未找到的，打印 `"未找到该特性"`
5. 为所有新代码添加 `///` 文档注释。
6. 运行 `cargo build`，修复所有编译错误直到通过。

**检查方式**：

```bash
cargo build   # 必须 0 错误通过
cargo run     # 输出中应包含特性查找的结果
```

**提示**：

- `const` 数组的类型标注是 `const FEATURES: [(&str, &str); 5] = [...]`
- `find_feature` 的返回类型是 `Option<&str>`，这是 Rust 处理「可能不存在」的标准模式，类似 Python 的 `None` 返回但类型安全
- 你可以使用 `for (name, desc) in FEATURES.iter()` 遍历，或者使用迭代器的 `.find()` 方法
- 处理 `Option` 时使用 `match`（Rust 的模式匹配）或 `if let` 语法
- 如果你还没有学习 `match` 或 `Option`，这是你第一次接触它们——这正是本练习的目的。不要怕，编译器会引导你：

```rust
match find_feature("Static Typing") {
    Some(desc) => println!("找到特性：Static Typing —— {}", desc),
    None => println!("未找到特性：Static Typing"),
}
```

## 思考题

**题目**：假设有一个 Python 项目，团队决定用 Rust 重写其中的性能敏感模块。在团队会议上，一位 Python 开发者说：

> "我们已经有类型提示和 mypy 了，为什么还要费那么大劲学 Rust？mypy 足够在 CI 中保证静态类型安全了吧？"

**请你从以下三个角度写出你的看法（每个角度 2–3 句话）：**

1. **类型系统层面**：Python 的类型提示（type hints）+ mypy 与 Rust 的编译期类型检查有什么本质区别？
2. **性能层面**：mypy 能帮助提升 Python 代码的性能吗？为什么？
3. **安全保证层面**：类型检查能防止 `NoneType has no attribute 'x'` 这样的错误，但能防止数据竞争（data race）和 use-after-free 吗？

**参考答案方向**（建议先自己写完再看）：

<details>
<summary>点击展开参考思路</summary>

1. **类型系统层面**：Python 的类型提示是可选的、运行时不检查的（由 mypy/pyright 等外部工具在 CI 阶段检查）。Rust 的类型系统是语言的底层基石，编译器在任何时候都强制执行类型规则，不正确的类型程序根本无法编译。此外，Rust 的类型系统还编码了所有权和生命周期信息，这是 Python 类型提示体系完全不涉及的概念。

2. **性能层面**：mypy 是静态分析工具，不修改运行时代码，对 Python 程序的执行速度没有直接影响。而 Rust 的类型系统和所有权规则使得编译器可以在编译时做激进的优化（内联、死代码消除、栈分配优化），同时不需要插入 GC 和引用计数的运行时检查。

3. **安全保证层面**：类型检查可以防止「调用了不存在的属性」这类接口错误，但无法防止：
   - 数据竞争：两个线程同时写同一个数据——这在 Python 中被 GIL「掩盖」了，但在 Rust 中可以通过 `Arc<Mutex<T>>` 等方式安全处理。
   - use-after-free：释放内存后继续使用指针——Python 的 GC 让程序员基本不需要手动管理内存，但 Rust 通过所有权系统在编译期证明不会发生这种情况。
   Rust 的安全保证远超纯类型检查，覆盖了内存安全和并发安全两大领域。

</details>

## 推荐检查命令

完成练习后，使用以下命令验证你的代码状态：

```bash
# 进入项目目录
```
