## Level 2：进阶练习

### 练习 2-1：遮蔽 vs mut 深度理解

编写一个程序，通过实际代码展示遮蔽（shadowing）和 `mut` 在以下方面的区别：

1. **作用域行为**：在内层作用域遮蔽一个变量，退出作用域后观察变量值的变化。对比 `mut` 变量在内层作用域的修改行为。
2. **类型变化**：演示遮蔽可以改变类型而 `mut` 不能。
3. **多次遮蔽**：对一个变量名进行至少 4 次连续的遮蔽操作，每次改变类型（如 `i32` -> `f64` -> `char` -> `&str` -> 元组），并在每一步之间打印。
4. **不可变性保留**：证明被遮蔽后的变量仍然是不可变的（除非显式使用 `let mut`）。

**要求**：
- 代码中需要有针对性的注释，解释每一步发生了什么
- 输出要清晰地展示每一步的结果
- 包含至少一处使用 `let mut` 的遮蔽
- 包含至少一处作用域嵌套的遮蔽演示

**预期理解**：完成这个练习后，你应该能够向别人清晰地解释"遮蔽是创建新绑定，mut 是修改原绑定"这一核心区别。

### 练习 2-2：实现安全数组工具函数

编写一个程序，包含以下函数：

1. `fn safe_get(arr: &[i32], index: usize) -> Option<i32>`  
   使用 `get()` 方法安全地获取数组元素，返回 `Option<i32>`。

2. `fn print_element(arr: &[i32], index: usize)`  
   调用 `safe_get`，使用 `match` 优雅地处理 `Some` 和 `None` 两种情况，打印相应信息。

3. `fn array_sum(arr: &[i32]) -> i32`  
   利用 for 循环计算数组中所有元素的和。不可以使用迭代器的 `sum()` 方法。

4. `fn swap_elements(arr: &mut [i32], i: usize, j: usize) -> Result<(), String>`  
   交换数组中两个位置的元素。使用 `get()` 进行边界检查，返回 `Result` 表示成功或错误信息。

5. 在 `main` 中测试所有这些函数：
   - 正常访问、越界访问
   - 求和
   - 正常交换、越界交换

**要求**：
- 所有函数都要显式标注类型
- 正确处理所有边界情况
- 在注释中标注哪些地方使用了 `usize` 类型，为什么用 `usize` 而不是 `u32` 或 `u64`
- 演示 `&[i32]` 切片参数的优势（既可以传数组引用也可以传 Vec 引用）

## Level 3：综合练习

### 练习 3-1：多维度的类型系统探索

编写一个综合程序，实现以下功能：

**第一部分：内存布局探索**

创建一个函数 `fn explore_memory()`，使用 `std::mem::size_of` 打印以下类型的大小：

- 所有 12 种整数类型（i8 到 i128, u8 到 u128, isize, usize）
- f32, f64, bool, char
- 单元元组 `()`
- `(i32,)` 和 `(i32, i32)` 和 `(i32, i32, i32)` —— 观察元组大小如何随元素增加
- `[u8; 0]`, `[u8; 1]`, `[u8; 16]`, `[u8; 64]` —— 观察数组大小
- `(bool, char)` 和 `(char, bool)` —— 观察字段顺序对大小的影响（结构体填充）

**第二部分：类型转换矩阵**

创建一个 4x4 的"合法转换矩阵"：取 `i32`, `u8`, `f64`, `char` 这四个类型，尝试所有方向的 `as` 转换。对于每次转换，打印源值、目标值和任何截断/损失的信息。

**第三部分：字符与 Unicode 探索**

- 创建一个包含 ASCII 字符、中文、emoji、数学符号的字符数组

- 解释为什么有些字符能/不能安全转换为 `u8`

**要求**：
- 代码组织清晰，使用合适的函数拆分
- 所有函数都需要文档注释（`///`）
- 在程序末尾打印一个总结，概括你从这三个部分的实验中学到了什么

## 思考题

### Rust 为什么设计"默认不可变"？

在大多数主流编程语言中，变量默认是可变的（如 Python、JavaScript、Java、C++）。Rust 却选择了相反的做法——变量默认不可变，需要可变时必须显式标注 `mut`。

请从以下角度思考并写下你的理解（每个角度至少写 3-5 句）：

1. **安全性**：默认不可变如何帮助防止 bug？你能否想到一个实际场景，其中默认不可变会阻止一个隐蔽的错误？
2. **并发**：不可变性如何与 Rust 的并发模型（" fearless concurrency "）相关联？
3. **编译器优化**：默认不可变给了编译器哪些优化机会？为什么 GCC/Clang 也为 C/C++ 提供了 `const` 关键字？
4. **代码可读性**：当你阅读 `let mut x = 5` 时，`mut` 关键字传达了关于 `x` 的什么信息？如果默认可变，你如何在阅读代码时知道哪些变量会被修改？
5. **个人体验**：在你自己的编程经历中（Python 或其他语言），有没有因为变量被意外修改而导致的 bug？如果语言默认不可变，这些问题是否会避免？

**提示**：尝试将你的思考写成 300-500 字的短文，用具体的代码示例支撑你的观点。

## 推荐检查命令

在完成每个练习后，运行以下命令验证你的代码：

```bash
# 编译检查（看到所有编译错误）
cargo build

# 运行程序
cargo run

# 检查是否有未使用的变量或导入（Rust 会给出警告）
cargo run 2>&1 | grep warning

# 使用 clippy 进行更严格的代码检查（需要安装：rustup component add clippy）
cargo clippy

# 查看编译器展开的宏和详细分析
cargo rustc -- -Z unstable-options --unpretty=expanded

# 格式化代码（需要安装：rustup component add rustfmt）
cargo fmt

# 运行测试
cargo test
```

> 提示：Rust 编译器的错误信息非常优秀。当遇到编译错误时，请**仔细阅读**错误信息全文——它不仅告诉你哪里错了，还会给出修改建议（`help:` 部分）。养成阅读完整编译错误信息的习惯，这是学好 Rust 的关键之一。
